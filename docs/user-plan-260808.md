# 2026年08月 ユーザー機能追加 詳細仕様書

このドキュメントは、2026年08月アップデートに向けたログイン・サインアップ機能およびログインユーザー専用機能の追加に関する詳細仕様書です。実装時は本仕様を正とします。

## 1. 基本方針

- 認証、認可、セッション、トークン、暗号処理はサーバー側で実施する。クライアントから渡されたユーザーID、ロール、閲覧可否、既読状態を信用しない。
- 記事本文の閲覧可否判定は共通関数に集約し、ページ、Route Handler、RSS、記事一覧、前後記事、画像取得、既読・Like APIなど、本文または本文由来データを扱うすべての経路から利用する。
- パスワード、認証・再設定用の生トークン、認証セッションIDは平文でも復号可能な暗号文でも保存しない。
- メールアドレスは表示・メール送信に必要な暗号文と、検索・一意判定に使用するHMAC値を別々に保存する。
- 匿名Like用Cookieとログイン認証Cookieは完全に分離する。
- アカウント自体に金銭的価値はないため、パスワード履歴や定期変更は導入しない。一方、メールアドレス、パスワードハッシュ、セッション、トークンの漏えい防止は必須要件とする。
- MFAは今回の必須範囲外とする。将来導入する場合はTOTPまたはパスキーを候補とし、特に管理者への導入を優先する。
- ログイン、サインアップ、設定、認証トークン処理のレスポンスは共有キャッシュへ保存しない。

## 2. DB共通方針とデータモデル

### 2.1 共通方針

- DB上のカラム名はPrismaの慣例に合わせ、`createdAt`、`updatedAt`などのcamelCaseを使用してよい。
- すべてのテーブルへ機械的に`flg`を追加しない。ユーザーには`deletedAt`、セッションには`revokedAt`、トークンには`expiresAt`など、状態の意味が分かるカラムを使用する。
- 監査ログや閲覧イベントのような追記専用データには`updatedAt`や論理削除フラグを必須としない。
- 日時はDBではUTCとして保存し、画面表示時にAsia/Tokyoへ変換する。
- ユーザー別の累計Like数・累計既読記事数は原則として関連テーブルから集計する。性能上キャッシュカラムを追加する場合は、関連レコードの更新と同一トランザクションで更新し、再集計手段も用意する。

### 2.2 User

最低限、以下を保持する。

- `id`: DB内部主キー。外部表示には使用しない。
- `readerNumber`: 正式登録順の読者番号。メール認証前はnull、認証成功時に1からの連番を採番し、uniqueとする。物理削除後も再利用しない。
- `emailEncrypted`: 正規化済みメールアドレスをAEAD方式で暗号化した値。
- `emailKeyVersion`: メール暗号鍵の世代。
- `emailHmac`: 正規化済みメールアドレスのHMAC-SHA-256。検索・重複判定用としてuniqueとする。
- `passwordHash`: Argon2idなど、パスワード保存専用アルゴリズムによるソルト付き不可逆ハッシュ。
- `verifiedAt`: メール認証日時。未認証はnull。
- `signedUpAt`: 最初にサインアップ要求を受け付けた日時。
- `lastLoginAt`: 最終ログイン成功日時。未ログインはnull。
- `handleName`: ハンドルネーム。未設定はnull。
- `role`: 整数。`10=管理者`、`1=一般ログインユーザー`とする。
- `createdAt`、`updatedAt`、`deletedAt`。

メールアドレスの正規化は、前後空白の除去とドメイン部の小文字化を最低限行う。ローカル部の大文字小文字やドットをメール事業者固有の規則で勝手に変換しない。`+`以降のエイリアス除去は表示名生成時だけに使用し、ログイン照合・一意判定では除去しない。

### 2.3 Session

- `id`: DB内部主キー。
- `userId`: Userへの外部キー。
- `tokenHash`: Cookieへ格納したランダムな生セッショントークンのHMACまたは安全なハッシュ。uniqueとする。
- `createdAt`、`lastUsedAt`、`expiresAt`、`revokedAt`。
- 必要に応じてUAのハッシュ、作成元IPのHMACを保持する。生のセッショントークンは保持しない。

### 2.4 EmailVerificationToken / PasswordResetToken

- `id`、`userId`、`tokenHash`、`expiresAt`、`createdAt`を保持する。
- 生トークンは暗号学的に安全な乱数として発行し、メールURLにのみ含める。DBにはHMACまたは安全なハッシュだけを保存する。
- EmailVerificationTokenは1ユーザーにつき有効なものを最大1件とする。
- トークンは用途をまたいで再利用しない。
- 使用済み、失効済み、再発行で置き換えられたトークンレコードは削除する。監査にはトークン値を含まないイベントだけを残す。

### 2.5 AuthAttempt

- 試行日時、処理種別、成否、失敗理由の分類、`emailHmac`、`ipHmac`、UA、相関用ハッシュを保持する。
- 入力されたパスワード、平文メールアドレス、生IP、Hostヘッダー、生セッションID、生トークンは保存しない。
- 相関用ハッシュはセッションまたは一連の認証処理を関連付けるために使い、元の秘密値を復元できないものとする。
- UAは長さ上限を設け、制御文字を除去してから保存する。
- 監査ログの保存期間は原則90日とし、定期削除する。

### 2.6 Like・既読・サイト設定

- 既存の`Like`テーブルは匿名Like用として維持する。
- ログインユーザーのLikeは`UserLike`で別管理し、`userId + articleId`をuniqueとする。有効状態とLike日時・更新日時を保持する。
- 現在の既読状態は`UserPostRead`で管理し、`userId + articleId`をuniqueとする。最初の既読日時と最後の既読日時を保持する。
- 閲覧履歴は追記専用の`ReadEvent`で管理し、`userId`、`articleId`、送信日時、サーバー側で検証・正規化したリファラを保持する。
- Introのお知らせは`SiteSetting`で管理し、設定キーをuniqueとする。

## 3. 暗号鍵・Secret管理

- メール暗号鍵、メールHMAC鍵、IP HMAC鍵、トークンHMAC鍵、セッションSecretは用途ごとに分離する。
- `EMAIL_ENCRYPTION_KEY`は32バイトのランダム値をBase64化したものとし、HMAC鍵・セッションSecretを含むすべての鍵は十分な長さの独立したランダム値を使用する。用途間で同じ値を再利用しない。
- ローカル開発では`.env`を使用してよいが、Gitへコミットしない。本番ではコンテナイメージへ埋め込まず、実行時環境変数またはSecret管理機構から注入する。
- `.env.example`には環境変数名、公開してよい既定値、生成方法だけを記載し、AWSアクセスキー、暗号鍵、HMAC鍵、トークンなどの実値を記載しない。`.env`が過去にGit管理されていた場合は、ローカルファイルを保持したまま追跡対象から外す。
- 暗号化データには鍵世代を保存し、将来の鍵ローテーションを可能にする。
- 本番DBバックアップも機密情報として暗号化・アクセス制限する。
- 想定する環境変数には、セッションSecret、各暗号・HMAC鍵、管理者メールアドレス、SESリージョン・送信元、AWS認証情報を含む。AWS権限はメール送信に必要な最小権限とする。

## 4. ログイン画面

### 4.1 フロントエンド

- `/login`にメールアドレスとパスワードの入力フォームを設置する。
- メールアドレスは妥当な形式のみ受け付ける。クライアント検証に加えて、サーバー側でも同じ制約を検証する。
- パスワードはUnicode、空白、英数記号を受け付け、文字種の組み合わせを強制しない。NUL文字と不正なUnicodeは拒否する。
- パスワードは12文字以上、UTF-8で256バイト以下とする。入力を黙って切り詰めない。
- パスワード条件の「12文字以上、UTF-8で256バイト以下」は、入力値が条件を満たさない場合だけバリデーションエラーとして表示し、常時表示のヘルプ文には使用しない。
- フォームの常時表示文言は「アカウントを作成することで最新の利用規約に同意したものとみなします。」とする。
- 「アカウント作成」「パスワード再発行」「ログイン」「トップページへ戻る」ボタンを設置する。
- ログインボタンとアカウント作成ボタンは、メールアドレスとパスワードが両方妥当な場合のみ押下可能とする。
- パスワード再発行ボタンは、メールアドレスが妥当なら押下可能とし、パスワード入力を必須としない。
- ログイン済みの場合はログインボタンをログアウトボタンへ変更する。ログアウトボタンは他の入力値に関係なく押下可能とする。
- 「トップページへ戻る」は入力値や認証状態にかかわらず利用可能とする。
- HTML metadataと`X-Robots-Tag`で`noindex, nofollow, noarchive`を指定し、robots.txtでもクロールを拒否する。ただし、これらをアクセス制御の代替にしない。
- 認証関連画面では認証値を分析基盤へ送らない。特にトークン付きURLをGoogle Analyticsへ送信しない。

### 4.2 ログイン処理

- 正規化メールアドレスから`emailHmac`を生成してUserを検索し、保存済みパスワードハッシュを安全な比較関数で検証する。
- メールまたはパスワードが誤っている場合は、存在有無を判別できない共通メッセージ、共通HTTPステータス、極端な処理時間差のない応答を返す。
- 未認証ユーザーについては、正しいパスワードの照合にも成功した場合だけ「メール認証が完了していません。ここをクリックするとメールを再送信します」と表示する。
- ログイン成功時は新しい認証セッションを発行し、`lastLoginAt`へ認証試行日時と同一の日時を記録してトップページへ遷移する。
- ログイン成功時は既存の認証セッションIDを引き継がず、必ず新しいセッショントークンを発行する。
- セッションCookieは匿名Like用`access_id`とは別名とし、本番では`__Host-`接頭辞、`HttpOnly`、`Secure`、`SameSite=Lax`または`Strict`、`Path=/`を設定する。
- 一般ユーザーのセッションは最終利用から30日、絶対期限120日を上限とする。
- 管理者セッションは最終利用から12時間、絶対期限30日を上限とする。
- ログアウト時はサーバー側セッションを失効させ、認証Cookieを削除する。匿名Like用Cookieは削除しない。
- パスワード変更、パスワードリセット、ユーザーのロール変更時は、そのユーザーの既存セッションをすべて失効させる。

### 4.3 ログイン試行ログとレート制限

- ログイン試行ごとにAuthAttemptを記録するが、入力パスワードと平文メールアドレスは絶対に記録しない。
- IPは信頼済みリバースプロキシの設定に基づいて取得し、永続保存前に鍵付きHMACへ変換する。`Host`や任意の`X-Forwarded-For`を無条件には信用しない。
- 同一`ipHmac`から10分以内に10回のログイン試行があった場合、その後1時間ログイン試行がなければ解除されるまで拒否する。
- IP単独ではなく、`emailHmac`単位の失敗回数とサイト全体の急増も監視する。共有回線の利用者全体を長時間ロックしないよう、拒否・遅延・追加検証を段階的に適用できる構造とする。
- 信頼できる送信元IPを取得できない場合、全利用者で共有する疑似IP識別子を作らず、IP単位の制限を省略して`emailHmac`単位とサイト全体の制限を適用する。
- レート制限状態はプロセスメモリだけに保持せず、単一インスタンス運用中はDBへ保持する。将来複数インスタンス化する場合は共有ストアへ移行する。

### 4.4 管理者ロールと通知

- 管理者候補は環境変数のメールアドレスを正規化・HMAC化し、メール認証済みユーザーの`emailHmac`と照合する。
- 一致したユーザーにはDB上で管理者ロールを設定する。リクエストごとにメール文字列だけから管理者権限を付与しない。
- 管理者ロールを付与・変更する処理は監査ログへ記録し、既存セッションを失効させる。
- 管理者ユーザーのログイン成功時は、登録メールアドレスへSESで通知する。1分以内に複数回成功した場合は最初の1回だけ送信し、抑制状態はDBで管理する。
- 通知メール送信失敗によってログイン自体を失敗させない。失敗は監査・再送対象とする。

## 5. サインアップとメール認証

### 5.1 アカウント作成要求

- `/login`でメールアドレスとパスワードを入力し「アカウント作成」を押すと、サーバー側で再検証したうえでサインアップ処理を開始する。
- Userへ`emailEncrypted`、`emailHmac`、`passwordHash`などを保存する。この時点では`verifiedAt`と`readerNumber`をnullとする。
- 同じ`emailHmac`を持つUserを複数作成できないようDBのunique制約で保証する。
- 既に認証済みのメールアドレス、または別のパスワードで作成済みの未認証メールアドレスに対しても、外部向けには「メールを送信しました。メールの指示に従って認証を完了してください」という共通メッセージを返し、アカウントの存在を開示しない。
- 未認証アカウントへの再送は、ログイン処理で正しいパスワードを検証できた場合に案内する。再送時にパスワードを上書きしない。
- メール認証トークンは有効時間30分とする。発行は`emailHmac`および`ipHmac`ごとに1時間10回までとする。
- 未認証ユーザーに既存トークンがある状態で再発行する場合、失効日時にかかわらず古いトークンを削除してから新しいトークンを登録する。
- DBへのUser・トークン登録が成功してからSESで認証メールを送信する。メール送信失敗時は安全な共通エラーを表示し、再送可能な状態を維持する。

### 5.2 メール認証

- メールには生トークンを含む検証専用URLを記載する。
- 検証URLはHTML画面を直接表示せず、専用Route Handlerでトークンを検証・消費してから、トークンを含まない`/welcome`へリダイレクトする。
- トークン比較は、受信した生トークンからHMACまたはハッシュを生成し、DBの`tokenHash`と安全に比較する。
- トークンが正しく有効期限内なら、1トランザクションで以下を実施する。
  - `verifiedAt`へ認証日時を記録する。
  - `readerNumber`へ正式登録順の次番号を採番する。
  - 管理者候補と一致する場合は管理者ロールを設定する。それ以外は一般ユーザーロールを設定する。
  - 使用したメール認証トークンを削除する。
- `readerNumber`の採番は同時認証でも重複しないよう、DBトランザクションとunique制約で保証し、競合時は安全に再試行する。
- 認証成功後の`/welcome`では「アカウント作成に成功しました。あなたは{readerNumber}番目の読者です。」と表示する。
- 期限切れの場合は古いトークンを削除し、「トークン期限が過ぎたためメール認証に失敗しました。もう一度メール認証を行ってください」と表示する。
- 不正、使用済み、存在しないトークンの場合は内部情報を開示せず、安全なエラーコードと問い合わせ用相関IDを表示する。
- `/welcome`にはトップページへ戻るボタンを表示する。
- 検証エンドポイントと`/welcome`には`no-store`および`X-Robots-Tag: noindex, nofollow, noarchive`を設定する。

## 6. パスワード再発行

### 6.1 再発行要求

- 入力されたメールアドレスを正規化して`emailHmac`で検索する。
- 該当する認証済みユーザーが存在する場合だけSESで再設定メールを送るが、画面のメッセージ、HTTPステータス、処理時間から存在有無を判別できないようにする。
- トークンの有効時間は30分、発行は`emailHmac`および`ipHmac`ごとに1時間5回までとする。
- 新しいトークンを発行する際は、そのユーザーの古いパスワード再設定トークンを削除する。

### 6.2 トークン交換とパスワード変更

- メール内URLの生トークンは専用Route Handlerで検証し、短命・一回限り・`HttpOnly`・`Secure`・`SameSite=Strict`のパスワード再設定Cookieへ交換したうえで、クエリ文字列のない`/password-reset`へリダイレクトする。
- `/password-reset`には新しいパスワードとConfirmの2入力欄、送信ボタンだけを表示する。
- パスワードポリシーを満たさない場合、または2つの入力が一致しない場合は送信できない。サーバー側でも同じ条件を検証する。
- パスワード条件は入力が条件を満たさない場合だけバリデーションエラーとして表示し、常時表示しない。
- 成功時は新しいソルト付き不可逆ハッシュへ更新し、再設定トークンと再設定Cookieを破棄し、そのユーザーの既存ログインセッションをすべて失効させる。
- パスワード変更完了通知を登録メールアドレスへ送信する。メール本文にパスワードを含めない。
- パスワードリセット後は自動ログインせず、`/login`で再ログインするよう促す。
- `/password-reset`とトークン交換エンドポイントには`no-store`および`X-Robots-Tag: noindex, nofollow, noarchive`を設定する。

## 7. CSRF・入力検証・レスポンス保護

- ログアウト、Like、既読、ユーザー設定、管理者設定などの状態変更はGETで実行しない。
- 状態変更APIでは、セッションに結び付けたCSRFトークンをカスタムヘッダーで検証する。あわせて`Origin`、`Sec-Fetch-Site`を検査し、許可していないcross-siteリクエストを拒否する。
- 認証セッション用CSRF Cookieと匿名Like用CSRF Cookieを明確に区別し、Cookie列挙順に依存せず、現在の認証状態に対応するトークンだけを送信する。
- JSON APIは想定した`Content-Type`だけを受け付け、サイズ上限を設定する。
- CORS許可リストは完全一致で管理し、Cookie付き通信でワイルドカードを使用しない。
- ハンドルネーム、Intro、UA、リファラ、エラー表示は出力先に応じてエスケープまたはサニタイズする。
- 認証・設定画面を含め、`X-Content-Type-Options`、適切な`Referrer-Policy`、`Content-Security-Policy`の`frame-ancestors`、本番HTTPSでのHSTSを設定する。
- 詳細な例外、SQL情報、ファイルパス、秘密値をユーザー向けエラーへ含めない。問い合わせに必要な場合はランダムな相関IDを表示し、詳細はサーバーログで追跡する。

## 8. ログイン中のトップページ表示

- サイトタイトルはIntro本文やユーザー情報と同じ行に置かず、トップ領域の最上段で単独の1行として表示する。
- サイトタイトルの次の行にIntro本文とユーザー情報領域を横並びで配置する。
- トップページのIntro領域右側、最大表示領域のおよそ3割をログインユーザー情報領域にする。
- 非ログイン時はユーザー情報領域を表示せず、現在と同じ表示とする。
- ユーザー情報領域は静的なトップページの初期描画後、認証Cookieを使用する`no-store`のユーザー情報APIから取得して表示する。初期HTMLや共有キャッシュへユーザー情報を含めない。
- 1行目に「ログイン中：{user}さん」と表示する。ハンドルネームがあればそれを使用し、なければ復号したメールアドレスのローカル部から表示用に`+`以降を除去する。
- 2行目に累計既読記事数と、現在Likeしている記事数を表示する。
- 3行目に最後に既読にした記事の記事番号・日付を表示し、クリックすると記事ページへ遷移する。現在の権限でメタ情報も表示できない記事は出さない。
- 4行目にFont Awesomeの`gear`アイコンを表示し、クリックすると`/config`へ遷移する。
- APIが未認証を返した場合は領域を表示しない。エラー時にメールアドレスなどの一部だけを残さない。

### 8.1 開発用ダミー認証

- `NODE_ENV=development`では、明示的に無効化されていない限り、初期状態を一般ログインユーザー相当のダミーユーザーとして動作させる。
- 開発環境のトップページ右上へ、画面レイアウトのフローから独立したfixed配置で「非ログイン」「ログイン」「管理者」の切替ブロックを表示する。
- ロール切替状態は開発専用のHttpOnly Cookieで管理し、ユーザーID、ハンドルネーム、Like数、既読数には開発専用のダミー値またはダミーユーザーのDB集計値を使用してよい。
- 開発用認証APIと切替UIは`NODE_ENV=production`では必ず無効化し、環境変数の設定だけで本番有効化できる構造にしない。

### 8.2 日付アーカイブナビゲーション

- `DateArchiveHeader`は認証セッションを`no-store`で後読みし、非ログインユーザーにはコンポーネント自体を表示しない。
- 一般ログインユーザーは2023年以降の年だけ選択可能とし、2004年から2022年までは表示するが選択不可とする。
- 管理者は2004年から現在年までのすべての年を選択可能とする。ただし現在年の未来月は従来どおり選択不可とする。
- トップページ本体の静的生成を維持し、認証状態によるナビゲーション差分を共有HTMLへ含めない。

### 8.3 非ログイン案内とログアウト

- 非ログイン時だけ、Intro領域の下へIntroと同じメッセージボックススタイルで「アカウントを作成すると2023年以降の記事を読めるようになります。」とログインアイコンを表示する。
- ログインアイコンは`/login`へのリンクとし、本文中へ「ログイン」などの追加文字列を表示する必要はない。
- ログイン時はIntro内のログインアイコンを「ログアウト」へ置き換え、Font Awesomeの`right-from-bracket`を表示する。
- ログアウト操作はCSRF対策済みPOST APIでサーバー側セッションを失効させ、認証Cookieを削除した後、非ログイン表示へ更新する。
- 開発用ダミー認証でログアウトした場合は、開発用ロールCookieも非ログインへ変更する。

## 9. 設定画面

- `/config`は認証済みユーザーだけが利用できる。未認証時は`/login`へ遷移させる。
- ハンドルネーム、現在のパスワード、新しいパスワード、Confirmの入力欄と送信ボタンを表示する。
- ハンドルネームだけを更新する場合はパスワード欄を空にできる。
- パスワードを変更する場合は現在のパスワードによる再認証を必須とし、新しいパスワードとConfirmが一致し、パスワードポリシーを満たす場合だけ更新する。
- パスワード変更時は既存セッションをすべて失効させ、再ログインを求める。
- 最近いいねした記事を最大50本表示し、サブタイトルに現在いいねしている記事数を表示する。
- 最近既読にした記事を`UserPostRead.lastReadAt`の降順で最大50本表示し、サブタイトルに`累計既読記事数 / 現在閲覧可能な掲載済み記事数`を表示する。
- 最近既読にした記事と累計既読記事数は履歴として扱い、現在のロールでは本文を閲覧できなくなった記事も`UserPostRead`が存在する限り含める。その記事はタイトル・日付・タグ・カテゴリだけを表示し、一覧上の既読`check`アイコンは表示しない。開発用ダミーユーザーで管理者から一般ログインユーザーへ切り替えた場合も同様とする。
- 閲覧可能記事数は固定式で近似せず、後述の共通閲覧判定を記事ごとに適用して計算する。
- 設定ページと関連APIは`no-store`とし、他ユーザーの情報を共有キャッシュへ保存しない。

## 10. 管理者専用設定

- 管理者が`/config`へアクセスした場合、一般ユーザー向け機能に加えてIntroのお知らせ編集フォームを表示する。
- 管理者機能の表示有無だけでなく、更新APIでも有効なセッションと管理者ロールを検証する。
- Introはプレーンテキストとして保存・表示する。将来MarkdownやHTMLを許可する場合は既存のサニタイズ処理と許可タグ一覧を利用する。
- 更新成功後はトップページのキャッシュを無効化する。反映は次回再生成時でよく、すべてのアクセスへリアルタイム反映する必要はない。
- 変更前後の値、実行ユーザー、日時、相関IDを監査ログへ残す。ただし秘密値は含めない。

## 11. 記事の掲載条件とロール別閲覧権限

### 11.1 共通前提

- 掲載遅延判定を最優先する。記事日付が現在のAsia/Tokyoの日付から7日前より後なら掲載前とし、管理者を含む全員が閲覧できない。
- 掲載前の記事は記事ページ・APIで404相当とし、一覧、検索対象、前後記事、RSS、最新10本の計算から除外する。
- 掲載済み記事について、閲覧権限がないとは本文および本文由来の画像を取得できないことを意味する。
- ロールは整数で定義し、`10=管理者`、`1=ログインユーザー`、非ログインは`0`とする。判定ではtruthy/falsyに依存せず、必要なロール値を明示的に比較する。

### 11.2 本文閲覧判定の優先順位

掲載済み記事に対し、以下を上から順に適用する。

1. 記事番号が正の整数でない場合は管理者のみ閲覧可能とする。
2. タグ「準非公開の記事」がある場合は管理者のみ閲覧可能とする。この条件は「特別公開中の記事」より優先する。
3. タグ「特別公開中の記事」がある場合は誰でも閲覧可能とする。
4. 記事番号が6955より小さい場合、すなわち1〜6954は管理者のみ閲覧可能とする。ただし前項の「特別公開中の記事」は例外とする。
5. 掲載済みで正の整数の記事を記事番号の降順に並べた先頭10本は、誰でも閲覧可能とする。準非公開記事も10本の件数には含むが、その記事自体は手順2により管理者以外閲覧不可とする。
6. 上記以外の記事はログインユーザーまたは管理者だけが閲覧可能とする。

記事番号6955は「6955より小さい」条件には含めない。欠番は想定しないが、最新10本は番号範囲ではなく、実在する掲載済み記事を降順に10件取得して決定する。

### 11.3 権限がない記事の表示

- 掲載済みだが本文閲覧権限がない記事ページは404にせず、記事番号、タイトル、日付、カテゴリ、タグ、文字数・更新日時など秘密でないフッター情報を表示する。
- 本文部分は「この記事は非公開に設定されています」などの共通メッセージへ置き換える。
- Likeボタンと既読ボタンは表示しない。対応APIへ直接アクセスされてもサーバー側で403を返し、状態を取得・更新しない。
- 年月・タグ・トップなどの一覧でも記事番号、タイトル、日付、カテゴリ、タグは表示できるが、本文は共通メッセージへ置き換える。
- 前後記事リンクには掲載済み記事のメタ情報を使用できる。掲載前の記事はリンク候補に含めない。

### 11.4 判定ロジックの適用範囲

- `post-visibility.ts`などに、掲載遅延・タグ・記事番号・最新10本・ロールを扱う純粋な共通判定を実装する。
- `post-detail.ts`、`archive.ts`、`recent-posts.ts`は、認可結果を確認するまで本文を呼び出し元へ返さない。
- `/api/single`、`/api/slug/*`、`/api/recent`、その他本文を返すRoute Handlerへ同じ判定を適用する。
- 公開APIで本文を要求された場合、非ログインユーザー相当で閲覧可能な本文だけを返す。認証Cookieにより結果が変わるAPIには`public`キャッシュを付けず、`private, no-store`とする。
- RSSは常に非ログインユーザー相当として生成し、非ログインユーザーが閲覧できない本文を含めない。
- RSSは公開条件変更後の古い抜粋を配信しないよう要求ごとに公開可否を再検証し、失効可能な内容へ長時間のstaleキャッシュを設定しない。
- 本文由来画像を配信する画像APIでは、その画像を参照する記事を特定して同じ権限判定を適用する。所有記事を安全に特定できない保護対象画像は返さない。
- 本文由来画像はURLが不変であるため、公開条件を毎回再検証できるキャッシュ設定とし、公開後に準非公開化された画像を古いpublicキャッシュから配信しない。
- `allPosts`などの記事一覧APIでは、必要性のないファイルパスや未掲載記事情報を公開しない。

## 12. キャッシュ・レンダリング方針

- ISRで得られているMarkdown本文表示速度を維持する。
- Markdownからサニタイズ済みHTMLへの変換結果は、記事ファイル、更新時刻、レンダリング日などをキーにしたユーザー非依存キャッシュとして保持する。
- 閲覧認可はキャッシュ済みHTMLをレスポンスへ含める前に、リクエストごとに実施する。権限がないレスポンスへ本文HTMLを埋め込まない。
- 閲覧認可に使用するタグ、掲載日、最新10本の集合は公開一覧用の長時間キャッシュから分離し、現在の記事ファイルを基準に算出する。
- トップページ本文は、最新10本の境界変更後に古い本文を静的HTMLから配信しないようリクエストごとに認可する。Markdown変換結果のユーザー非依存キャッシュは維持し、ユーザー情報領域はクライアント側の`no-store` APIで後から読み込む。
- 個別記事や本文付きアーカイブのうち、ログイン状態によって本文が変わるレスポンスは動的に認可する。ただし重いMarkdown変換は前述のキャッシュを再利用するため、毎回変換しない。
- Likeと既読の状態・ボタンは本文レンダリング後にクライアントから`no-store` APIで読み込む。
- 公開メタ情報と公開本文のキャッシュ、認証済みユーザー情報のキャッシュを混在させない。Cookieにより変化するレスポンスへ`public`、`s-maxage`を設定しない。
- Intro更新後は`revalidatePath`またはタグベースの無効化を行う。即時性は保証しないが、通常の再生成を待たず反映できる設計とする。

## 13. Like機能

### 13.1 匿名ユーザー

- 既存の匿名Like用Cookie `access_id`と既存Likeレコードを継続利用する。
- 既存匿名Likeを、後から作成・ログインしたユーザーのUserLikeへ移行しない。
- 匿名ユーザーが閲覧権限のある記事でLikeすると匿名Likeとして記録し、同じCookieで再訪した場合は押下済み状態を復元する。

### 13.2 ログインユーザー

- 有効な認証セッションがある場合、匿名Like機能を使用せず、常にUserLikeを読み書きする。
- `userId + articleId`の一意制約とトランザクションまたはupsertにより、並行リクエストでも重複レコードを作らない。
- ユーザーが記事をLikeした状態は再訪時にも復元する。取り消した場合は非Like状態として保存する。
- ユーザーの「累計いいね数」は、現在有効にLikeしている記事のユニーク件数とする。押下回数や取り消し済みLikeは数えない。
- 記事上に表示する総Like数は、既存の有効匿名Like数と有効UserLike数の合計とし、既存表示を維持する。
- Likeボタンはアイコン・件数を含め、総Like数が0件なら`#ffffff`、1件以上なら`#ff62c6`で表示する。ログインユーザー本人のLike状態ではなく総Like数で色を決める。
- 記事個別ページ、トップページの新着記事10本、月別記事一覧など本文表示を伴う記事フッターでは、現在のユーザーがLike済みの場合に限り、Likeアイコンと件数を当該記事年の`YEAR_COLOR_HEX`へ変更する。この指定は通常の1件以上カラーより優先する。
- アカウント削除機能は今回実装しないため、削除時のUserLike処理は対象外とする。

### 13.3 API

- Likeの取得・更新前に、現在のユーザー区分と記事本文の閲覧権限をサーバー側で検証する。
- 状態変更にはCSRF対策を適用する。
- GETはユーザー別状態を含むため`private, no-store`とする。総Like数だけを返す公開APIを分ける場合、その結果だけは短時間の公開キャッシュを許可できる。
- 本文を複数表示するトップ・月別・タグ別一覧では、対象記事群のLike件数と現在ユーザーのLike状態を1回のバルクAPIで取得し、記事ごとの初期状態GETを発生させない。
- Likeの切替更新は単一の原子的なDB文として実行し、並行リクエストによる読み取り後更新の取りこぼしを避ける。

## 14. 既読判定と閲覧イベント

- ログインユーザーが閲覧権限のある記事本文を正常に読み込んだ場合、現在の既読状態をAPIから取得する。
- 既読・未読にかかわらず、以下の発火条件を満たしたら閲覧APIを非同期送信する。
- 記事ごとの1回のページ読み込みにつき、自動・手動を合わせて送信は最大1回とする。

発火条件は以下とする。

- 本文が正常に読み込まれ、既読アイコンが画面上に表示されたとき。初期表示時点ですでにアイコンが表示されている場合は、少しでも下方向のスクロール操作があった時点で発火する。初期表示時点で表示されていない場合は、アイコンが表示領域へ入った時点で発火する。
- 自動発火前にユーザーが既読アイコンを手動押下した場合。本文の読み込みに成功し、閲覧権限がある場合だけ有効とする。

API受信時は以下を行う。

- 有効な認証セッションと、対象記事の本文閲覧権限をサーバー側で再検証する。
- `UserPostRead`がなければ作成し、あれば`lastReadAt`を更新する。
- 既読・未読にかかわらず`ReadEvent`を1件追加する。
- 同一ページ読み込みからのネットワーク再送で重複しないよう、クライアントが生成した一回限りのイベントIDを受け取り、`userId + eventId`などのunique制約で冪等性を保証する。ただしユーザーIDはセッションから決定する。
- リファラは許可した長さ・形式に正規化し、認証トークンなどを含むクエリ文字列を保存しない。

フロントエンドは以下のとおりとする。

- 既読アイコンをLikeアイコンの隣に設置する。
- Font Awesomeの`square`を未読、`square-check`を既読として表示する。
- 既読ボタンはアイコンと文言を含め、未読なら`#ffffff`、既読なら`#62ff9c`で表示する。
- 記事個別ページ、トップページの新着記事10本、月別記事一覧など本文表示を伴う記事フッターでは、既読状態のアイコンと文言を当該記事年の`YEAR_COLOR_HEX`で表示し、通常の既読カラーより優先する。
- 閲覧イベント送信後は既読表示へ更新する。
- 非ログインユーザー、掲載前の記事、本文閲覧権限のない記事では既読アイコンを表示しない。
- Likeアイコンも本文閲覧権限のない記事では表示しない。

### 14.1 メタ情報記事一覧と既読状態

- 本節の「記事一覧」は本文を表示せず、記事番号、タイトル、日付、タグ、カテゴリなどのメタ情報を並べる一覧を指す。トップページの新着記事10本や月別記事一覧など本文表示を伴う領域は含めない。
- トップページの直近100本一覧、記事ページの「同じタグを含む記事」「前後の記事」、年別ページの記事一覧、ユーザー設定ページの「最近いいねした記事」「最近既読にした記事」は、表示形式を引数で切り替えられる単一の共通コンポーネントを利用する。
- 共通記事一覧コンポーネントは親Containerの横幅100%を使用する。
- 記事個別ページの「前後の記事」一覧は1か所だけに表示し、同等の近傍記事一覧を重複表示しない。
- 一覧内の現在記事へ適用する`.post-block-current`は、タグを含むすべての文字色を`#333`に統一する。
- ログイン時、上記一覧の日付直後には、既読の場合だけFont Awesomeの`check`アイコンを表示する。未読の場合は何も表示しない。
- 一覧上では「既読」「未読」の文字を表示せず、既読状態によって色を変更しない。`check`アイコンは配置先の文字色を継承する。
- 非ログイン時および現在のロールで本文閲覧権限がない記事では、一覧上の既読アイコンを表示しない。
- 一覧の各記事から既読APIを個別呼び出ししない。認証セッションから決定したユーザーIDと対象記事ID群を使い、一覧APIまたはバルク既読状態APIのデータ生成時に1回のDB検索で既読記事IDを取得する。
- トップ本文一覧、年月本文一覧のフッター既読ボタンも同じバルク結果を初期値として利用し、記事ごとの初期状態GETを発生させない。記事個別ページのフッターは単一記事のため従来の状態取得APIを利用できる。
- トップページの新着記事10本と月別記事一覧では、日付・タグ・カテゴリ領域に一覧用既読アイコンを表示しない。

## 15. Amazon SES

- SESで送信元ドメインIdentityを作成し、DNSへEasy DKIMのCNAMEレコードを登録して検証する。
- SPFとDMARCを設定し、可能なら専用のMAIL FROMドメインも設定する。
- SES Sandbox中は検証済み宛先にしか送れないため、本番公開前にProduction accessを申請する。
- 送信元アドレス、AWSリージョン、バウンス・苦情の監視方法を運用設定として定義する。
- AWS資格情報にはSES送信に必要な最小権限だけを付与し、本番実行時Secretとして注入する。
- 送信を担当するIAMユーザーまたはロールには、対象Identity・送信元へスコープを限定した`ses:SendEmail`を付与し、Rawメールを利用する場合だけ`ses:SendRawEmail`を追加する。
- 開発環境からの疎通確認にはAWS公式SESメールボックスシミュレーターを使用できる。実在宛先へ送信する前に、リージョン、送信元Identity、IAM権限をシミュレーター送信で検証する。
- 認証メール、パスワード再設定メール、パスワード変更通知、管理者ログイン通知のテンプレートを用途別に分ける。
- メール送信ログへ生トークンやメール本文を記録しない。

## 16. SQLite・migration・運用

- 現時点では単一コンテナ・個人ブログ規模を前提としてSQLiteを継続利用できる。
- 認証ログ、ReadEvent、Sessionの増加を監視し、必要に応じてWAL、busy timeout、適切なindexを設定する。
- 複数アプリケーションインスタンスから同じSQLiteファイルへ書き込む構成は採用しない。複数インスタンス化する場合はPostgreSQLなどへ移行し、レート制限も共有ストア化する。
- 本番ではマウント済みDBに対して、アプリ起動前または独立したデプロイ工程で`prisma migrate deploy`を実行する。イメージビルド中のDBだけにmigrationを適用して完了としない。
- Docker開発サービスではホストのビルド成果物と開発サーバーの`.next`を共有せず、コンテナ専用ボリュームへ分離する。ホストでの本番ビルドと開発サーバーの同時実行による成果物破損を防ぐ。
- `.env`、一時DB、DBバックアップを`.dockerignore`で除外し、DockerfileからはPrisma schemaとmigrationなど実行に必要なファイルだけを明示コピーする。Secretは最終イメージやbuilderキャッシュへ含めない。ビルド時に必要な`NEXT_PUBLIC_*`の公開値は明示的なbuild argumentで渡す。
- 記事ファイル一覧・記事メタ情報のプロセス内キャッシュは、同一Nodeプロセスのページ・Route Handler間で共有する。キャッシュ未生成時に複数リクエストが並行した場合は生成中Promiseを共有し、全Markdown走査を重複実行しない。
- ユーザー別既読状態、Like状態、セッション情報は上記の公開記事メタキャッシュへ混在させない。
- 大量の記事リンクを表示するSideMenuはNext.jsのクライアント遷移を使用するが、大量の事前fetchは無効化する。取得中表示、Abort処理、失敗時表示を実装し、旧来の同期全記事走査をページ遷移経路で使用しない。
- migration前にDBバックアップを取得し、migration失敗時の復旧手順を用意する。
- schema変更は既存匿名Likeレコードを破壊しない。UserLikeは別テーブルとして追加する。
- 期限切れトークン、失効・期限切れセッション、90日を超えたAuthAttemptを定期削除する。
- ReadEventは件数を監視し、長期保存が不要になった場合に集計後アーカイブまたは削除できるようにする。
- DBとバックアップのファイル権限をアプリ実行ユーザーへ限定し、外部公開ディレクトリへ配置しない。
- DBファイルと生成バックアップは`0600`、バックアップディレクトリは`0700`相当とし、起動・バックアップ作成時に権限を検証・補正する。起動時migrationだけを初期権限で実行し、HTTPサーバープロセスは専用の非root UID/GIDへ権限を落として起動する。
- 定期再検証を有効にする本番環境では`REVALIDATE_SECRET`を必須設定とし、未設定のまま更新が停止した状態で起動しない。

## 17. 必須テスト

- パスワード、生トークン、生セッションID、平文メール、生IPがDB・アプリログへ残らないこと。
- 同一メールアドレスの並行サインアップでUserが重複しないこと。
- 同時メール認証でも`readerNumber`が重複しないこと。
- 期限切れ、再発行前、使用済み、用途違いのトークンを受け付けないこと。
- ログイン、パスワード変更、リセット、ログアウトでセッションが適切に発行・失効すること。
- CSRF、許可されないOrigin、不正Content-Typeの状態変更要求を拒否すること。
- 管理者、一般ログインユーザー、非ログインユーザーについて、掲載遅延、準非公開、特別公開、1〜6954、最新10本、それ以外の組み合わせを表形式で網羅すること。
- ページ、`/api/single`、`/api/slug/*`、`/api/recent`、RSS、画像APIのどの経路からも権限のない本文・画像を取得できないこと。
- 認証済みレスポンスやユーザー情報が共有キャッシュから別ユーザーへ返らないこと。
- Likeと既読APIの並行・再送リクエストで重複や累計値のずれが発生しないこと。
- 認証用と匿名Like用のCSRF Cookieが同時に存在し、Cookie列挙順が異なる場合も、各操作が正しいCSRFトークンを送信すること。
- 既存匿名Likeがmigration後も匿名ユーザーとして利用でき、ログインユーザーへ自動移行されないこと。
- Intro更新後のキャッシュ無効化と、HTML・スクリプト入力の無害化を確認すること。
- Like総数0件・1件以上、未読・既読の各状態で指定色が適用されること。
- 非ログイン、一般ログイン、管理者で`DateArchiveHeader`の非表示・年リンク無効・全年リンク有効が切り替わること。
- 開発用認証UI・APIが本番ビルドでは利用できないこと。
- トップ直近100本、年別、同一タグ、前後記事、ユーザー設定のいいね・既読記事一覧で既読状態取得が記事件数分の通信にならず、1表示領域につき1回のバルク取得になること。
- 年別ページとユーザー設定ページの共通記事一覧が親Containerの横幅100%を使用すること。
- 記事個別ページで「前後の記事」一覧が重複せず、現在記事の文字色がタグを含めて`#333`になること。
- メタ情報記事一覧では既読記事だけに`check`が表示され、未読記事にはアイコンも既読・未読の文言も表示されないこと。
- トップ新着10本・月別記事一覧ではヘッダーの日付・タグ・カテゴリ領域に既読アイコンがなく、フッターのLike済み・既読状態が記事年の`YEAR_COLOR_HEX`になること。
- トップ新着10本・月別記事一覧など本文付き一覧でLike初期状態取得が記事件数分の通信にならず、1表示領域につき1回のバルク取得になること。
- 非ログイン案内、ログイン時のログアウト表示、ログアウト後のセッション失効と非ログイン表示を確認すること。
- 記事個別ページでLike済み・既読の色が記事年の`YEAR_COLOR_HEX`と一致すること。
- キャッシュが空の状態でSideMenu、Like、既読APIが並行しても全記事メタ生成が重複せず、SideMenuが欠落・エラーにならないこと。
- 本番相当のマウント済みSQLite DBへmigrationが適用され、既存データを保持したまま起動できること。
- DB一意制約、並行更新、レート制限を検証する結合テストでは`TEST_DATABASE_URL`を必須とし、未設定によるskipをリリース判定上の成功として扱わない。
