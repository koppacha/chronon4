# ユーザー機能 実装・テスト計画

対象仕様: `docs/user-plan-260808.md`

## 1. 実装方針

実装は、認証基盤、記事認可、ユーザー機能、運用・テストの順に進める。UIから先に実装せず、すべてのRoute HandlerとServer Componentが共用できるサーバー側の認証・認可関数を先に完成させる。

Markdown変換結果のプロセス内キャッシュは維持する。ログイン状態で本文の閲覧可否が変わるページはリクエスト単位で認可するが、認可後に既存の変換済みHTMLキャッシュを再利用し、Markdown変換を毎回実行しない。

## 2. 実装フェーズ

### Phase 1: DB・暗号・セッション基盤

1. PrismaへUser、Session、EmailVerificationToken、PasswordResetToken、AuthAttempt、UserLike、UserPostRead、ReadEvent、SiteSettingを追加する。
2. 既存Likeは匿名用として保持し、既存データを変更しないmigrationを作成する。
3. メール暗号化・メール/IP/トークンHMAC・パスワードハッシュ・ランダムトークン生成を実装する。
4. 認証Cookieの発行・取得・ローテーション・失効と、匿名Cookieとの分離を実装する。
5. CSRFトークン、Origin、Sec-Fetch-Site、Content-Type検証を共通化する。
6. DBベースのログイン・メール送信レート制限と認証監査ログを実装する。

完了条件: 暗号処理と認証境界の単体テストが通り、生秘密値がDBへ保存されない。

### Phase 2: 認証フローと設定

1. `/login`、ログイン・ログアウト・サインアップ・認証メール再送APIを実装する。
2. SES送信層を実装し、未設定の開発環境では生トークンをログへ出さず安全に送信不能を返す。
3. メール検証専用Route Handlerと、クエリ文字列のない`/welcome`を実装する。
4. パスワードリセット要求、トークン交換、`/password-reset`、変更完了通知を実装する。
5. `/config`とユーザー情報APIを実装する。
6. 管理者のIntro更新、監査、トップページ再検証を実装する。

完了条件: 登録、検証、ログイン、ログアウト、再送、リセット、設定変更の正常系・異常系テストが通る。

### Phase 3: 記事認可とキャッシュ

1. 掲載遅延、非自然数、準非公開、特別公開、1〜6954、最新10本、ロールを扱う共通ポリシーを実装する。
2. `post-detail.ts`、`archive.ts`、`recent-posts.ts`をメタ取得と本文取得へ分離し、認可前に本文を返さない構造へ変更する。
3. 個別記事、トップ、年月・タグ一覧、前後リンクへ共通ポリシーを適用する。
4. `/api/single`、`/api/slug/*`、`/api/recent`、RSSへ共通ポリシーを適用する。
5. 本文画像APIへ所有記事の認可を適用し、判定不能な保護対象画像を拒否する。
6. Cookie依存レスポンスの共有キャッシュを禁止し、本文HTMLキャッシュはユーザー非依存のまま維持する。

完了条件: 権限マトリクスと全取得経路の結合テストで本文漏えいがない。

### Phase 4: Like・既読・トップユーザー領域

1. Like APIを匿名LikeとUserLikeへ分岐させ、upsert相当のトランザクションで重複を防ぐ。
2. 既読状態取得と冪等なReadEvent記録APIを実装する。
3. Like・既読ボタンを本文レンダリング後に読み込み、閲覧権限がない場合は表示しない。
4. トップページのユーザー情報領域を`no-store` APIから後読み込みする。
5. `/config`に最近のLike・既読一覧と集計値を表示する。

完了条件: 匿名Likeの後方互換、ユーザーLike、既読の再送・並行更新テストが通る。

### Phase 5: 運用・品質確認

1. 本番起動前migration、バックアップ、期限切れデータ削除の運用処理を追加する。
2. セキュリティヘッダー、認証ページのrobots指定、GA除外を確認する。
3. TypeScript、単体・結合テスト、production buildを実行する。
4. Webアプリ全体を対象にCodex Security標準スキャンを実行し、妥当な所見を修正する。
5. Playwrightで主要画面、フォーム検証、公開記事、権限なし表示、レスポンシブ表示を確認する。

完了条件: build、テスト、セキュリティ再確認、ブラウザ確認が完了し、残課題が文書化されている。

## 3. テスト方針

### 単体テスト

- メール正規化、HMAC、暗号化・復号、パスワード検証。
- トークン期限、セッション期限・失効、CSRF・Origin検証。
- 記事権限の全優先順位と最新10本の算出。
- Like・既読の集計と冪等性。

### API・DB結合テスト

- サインアップ並行実行時のメール一意性とreaderNumber採番。
- ログイン成功・失敗・未認証・レート制限。
- トークンの正常、期限切れ、再発行前、使用済み、用途違い。
- パスワード変更・リセット後の全セッション失効。
- CSRF、Origin、Content-Type拒否。
- 非ログイン、一般、管理者の本文・Like・既読API権限。

### 回帰・ビルド

- 既存匿名Like、トップ、個別記事、年月・タグ、RSS、サイドメニュー。
- `npm run build`による型検査とproduction build。

### セキュリティ確認

- リポジトリ全体の標準スキャン。
- パスワード、生トークン、生セッション、平文メール、生IPの保存・ログ出力がないこと。
- API直叩きとキャッシュによる本文漏えいがないこと。
- XSS、CSRF、IDOR、パストラバーサル、情報露出、レート制限回避を確認する。

### ブラウザ確認

- `/login`の入力制御とrobots指定。
- トップページの未ログイン表示。
- 公開記事、権限なし記事の表示差分。
- Like・既読ボタンの表示条件。
- `/config`の未ログインリダイレクト。
- デスクトップ・モバイル幅でのレイアウト崩れとコンソールエラー。

## 4. 計画妥当性チェック

- 認証より先にUIを作らず、サーバー側境界を先行するため、UIだけで権限を隠す事故を防げる。
- 認可共通化を記事取得層と全公開経路へ適用するため、既存の`PostBodyGuard`だけに依存しない。
- 動的認可とMarkdown変換キャッシュを分離するため、既存ISR導入理由である本文変換性能を維持できる。
- 匿名LikeとUserLikeを分離するため、既存データを壊さずログインユーザーの一意性を保証できる。
- 状態テーブルとイベントテーブルを分けるため、累計既読記事数と再読回数を矛盾なく扱える。
- SQLite単一インスタンスという現行運用制約内では実装可能である。複数インスタンス化は本計画の対象外とする。
- SES実送信、公開DNS、Production accessは外部AWS設定を必要とする。ローカルでは送信層をテストダブルへ置換して検証し、本番疎通は認証情報設定後の運用確認事項とする。
- ブログ本文は作業対象外とし、テストでは既存メタ情報を直接大量読込せず、ポリシー用fixtureを利用する。

以上より、外部AWS設定を除くアプリケーション実装・自動テスト・ローカル動作確認は現行リポジトリ内で実施可能と判断する。
